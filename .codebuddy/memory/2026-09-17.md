- **行业惯例核实**：RTK 静态测量精度用"对均值/真值的均方根 RMS = sqrt(mean(deviation^2))"；std(ddof=1) 是样本标准差（另一统计量）。mean(up)≈0 时两者数值近似但定义不同。

  - 现在两文件全部 `vertical_rms = np.sqrt(np.mean(up**2))`。
- **保留不动**的 std(ddof=1)：assess_static_stability 的 vert_rms、chart_en_scatter 的 sigma_u、报告 up_std——这些是"标准差"语义（离散度/不确定度椭圆轴），应继续用样本标准差。规则定为：**RMS 一律 sqrt(mean(x^2))，std 一律 ddof=1**，跨设备统一。

## 追加：北云报告"周期性/实际频率/插入性"部分 N/A 的修复（2026-09-17 第五轮）

### 用户问题

## 追加：华测 Position Accuracy 图"3根线全为0/直线"的根因与修复（2026-09-17 第六轮）

3. 真正导致"看成直线"的缺陷：旧代码给每个子图叠加 axhline(hgt_sigma=9.5962) 的灰色参考线，把 Y 轴上限撑到 10 m，而动态量只有 0.002~0.011 m，全被压到轴底、肉眼误读为"0 直线"。

### 与北云的可比性结论（重要，勿推翻）
- 北云 BESTGNSSPOSA 的 lat/lon/hgt σ 逐历元实时更新（实测 437 个唯一组合），所以北云直接画该字段即有波动。

- 两设备取的是"同一物理意义（定位不确定度、单位都是米）但各自设备里真正随时间更新的那个字段"：北云=BESTGNSSPOSA位置σ，华测=GNGST的rms/major/minor。这是合理器件差异，评估层（收敛判断/量级评估）算法完全复用、单位统一为米、结果可比。
- 不能强行让华测也画 BESTPOSA 位置σ（恒为定值，画了也是直线且无意义）。

## 追加：华测 COM11 二进制混合流——字节流锚点+CRC校验提取器（2026-09-17 第八轮）

### 用户问题
ENVSTATUSA 等消息被嵌在二进制乱码块里(约每1秒嵌一次)，要求：1)把被切断的数据提取出来；2)排查其他字段是否同样被嵌入，用一套统一程序以"字段名/字段头为提取要素"全部救回。

### 根因定位（实测字节，零猜测）
华测 COM11 日志是【不定长原始二进制块 + ASCII 报文】交错流(非 NovAtel 标准二进制帧)。
- 二进制块含大量 >=0x80 高字节与 NUL(全文件160059个NUL)，聚类约10037块，块长1~700字节不等。
- 二进制块内部不含 CRLF，但会拦腰切断本应一行一条的 ASCII 报文 -> 按行读取时该报文被劈成两段/污染，split/parse 时整条丢弃。
- 实测：#ENVSTATUSA 字节流出现 13959 次，按行解析仅 12575 条，丢失 1384 条正是被切断者。
- 北云 _com3.dat 实测 0 NUL、0 高字节，纯净无此问题(华测 COM11 特有)。

### 解决方案（gps_rtk_analyzer_huace.py，编译通过）
新增 extract_valid_messages(raw_bytes)：
- 锚点：_HASH_HEADS(9个#类: BESTPA/BESTPOSA/BESTVA/RTKPA/RTKVA/ENVSTATUSA/BESTDOPSA/SATVIS2A/RANGEA) + _NMEA_HEADS(9个$类: GNGGA/GNGSA/GNGST + 6种GSV)。
- 对每个锚点在 +700 字节窗口内找 '*' 校验结尾，用 CRC-32(#类,表4-6 初值0 多项式0xEDB88320,域='#'后'*'前,复用既有 _crc32_block) 或 NMEA XOR($类) 验证完整性。
- 只保留校验通过者 -> 天然剔除被二进制污染的残缺段，实现"以字段头为提取要素"的健壮恢复，全程以报文自带校验位为准、零猜测。

## 第九轮(续)：VDOP 补充 + 均值全0 + GSA合并bug修复

### 1. VDOP 来源与统一(回答用户三问,均有依据)
- **BESTDOPSA 无 VDOP**：手册 3.2.12 实测字段 pdop/gdop/hdop/tdop/htdop，无 vdop(华测实测 pdop=0.8013/gdop=0.9233/hdop=0.4138/tdop=0.4587/htdop=0.8725)。
- **VDOP 取自 GSA**：NMEA GSA 第17字段即 VDOP(fields[15]=PDOP,[16]=HDOP,[17]=VDOP)。
- **DOP 是接收机本地解算、非卫星播发**：手册原文"由接收机当前跟踪并在位置解中使用的卫星的几何分布算出"——即用【全部在用卫星】统一几何解算，不是分星座各算各的。
- **多星座 GSA 如何统一成一个 VDOP**：华测每历元发多条 GNGSA(每星座一条)，但同历元所有星座条的 PDOP/HDOP/VDOP 完全相同(实测100/100组一致)。故任取一条即得统一 VDOP。

### 2. merge_gsa_dop_per_epoch 重大 bug 修复(华测)
- **旧逻辑错误**：按"DOP 三元组相同"分组合并。静态场景 DOP 在连续多历元间完全不变，导致 83754 条仅合并出 17 组(应为 13959 历元)，DOP 时序/统计严重失真。
- **修复**：改用【PRN 星座签名】判历元边界——一个历元内各星座条按固定顺序循环，当某条首 PRN 与组首条首 PRN 相同即进入下一历元。修复后 83754 -> 13959 历元(=83754/6，与消息率一致)。
- 定位：huace `merge_gsa_dop_per_epoch`(parse_bestdopsa 前)。dop_data 主路径+GUI 均 GSA 优先(含 VDOP)、BESTDOPSA 兜底。
- 验证：DOP 统计表 VDOP min0.60/max0.80/mean0.70/std0.02；时序图 VDOP 蓝线 0.6-0.8 真实变化，横轴满 13960s。

### 3. 统计表"均值全0"——非bug，是定义使然(已加说明)
- ENU 偏移是"相对均值位置"计算：mean_lat/lon/hgt 为基准，各点先减均值再得 east/north/up。故均值恒为0，是数学定义、非巧合、非数据异常。
- 静态精度(重复性)分析本就以均值为中心看散布。
- 已在两套 huace+bynav 的 HTML+MD 共4处"均值"行加标注"（以均值位置为基准的相对偏移，均值定义上恒为 0）"，并统一为 0.0000 四位小数。
- 定位：huace HTML2660/MD3121；bynav HTML2748/MD3192。

### 4. bynav 无同类问题
- 北云用 $GPGSA(GPS-only, GP前缀)，每历元仅1条 GSA，parse_gsa 已含 vdop，无需合并，无此 bug。VDOP 实测 min0.70/max1.00/mean0.80/std0.08。

### 5. 关键工程教训(防复发)
- **文件编码**：两套 .py 均为 UTF-8 无 BOM + LF。PowerShell 默认 GBK 读取会显示乱码(仅显示假象，文件未坏)；务必用 [System.IO.File]::ReadAllLines(..,UTF8) 或 python io.open(..,encoding='utf-8')。写回绝不带 BOM、保持 LF。
- **GSA 分组合并绝不能用 DOP 值做键**(静态下 DOP 长时间不变)，必须用能区分历元的信号(如 PRN 星座签名/时间戳)。
- 输出目录：huace `..._output_v7`，bynav `..._com3_output_v7`。CLI `python -X utf8 gps_rtk_analyzer_X.py <input> -o <out>`。

## 第十二轮：消息周期/均匀性统计"造假"修复 + 事件型消息标 N/A

### 用户问题
北云数据统计里每条消息都显示 0.200s/5.00Hz/均匀(CV=0.00)/🟢符合，"很假"；且有些消息可能本非周期发送，应按手册标 N/A。

### 根因(数据+手册实证)
1. **# 类报文真实周期**：BESTGNSSPOSA/HEADINGA/TRACKSTATA/INSPVAXA/BESTPOSA 头含 TOW(索引6,秒)，实测相邻间隔全为 0.2s/0.1s(7002条间隔分布{0.2:7002})，是真周期，统计有效。
2. **GSV/GSA 周期是伪造的**：这些 NMEA 报文本身无时间字段(实测 $GPGSV/$GPGSA 无 UTC 时间)。原 build_real_message_periods 第二遍用 GGA 时间轴把每历元多条 GSV 全映射到同一历元时间，sorted(set()) 折叠成 1 条/历元 → 所有 GSV 假显示 0.200s/CV=0.00。实测 GSV 每历元条数随可见星数变化(GBGSV 4~5、GPGSV 1~2、GLGSV 2~3)，同历元各条背靠背同时发出，单句周期本就无意义。
3. **GGA/GST 真周期**：$GPGGA/$GPGST 含 UTC 时间字段(015733.20)，可实测，0.2s 真周期。

### 手册依据(北云 UG016 §3.1.12 LOG, p26)
消息是否有周期由 Trigger 字段决定：ONTIME=按周期输出；ONNEW/ONCHANGED=数据变化才输出(事件型)；ONCE=单次；ONMARK/ONNEXT。故标称周期取决于配置，实测周期取决于报文是否带时间戳。

### 修复(bynav + huace 同步)
- 新增常量 PERIOD_MEASURABLE(#类 + NMEA GGA/GST)/PERIOD_NOT_MEASURABLE(GSA/GSV)。
- bynav 删除 build_real_message_periods 第二遍 GGA 映射(造假源)；huace 本就无此映射，无需删。
- 两套 HTML+MD 渲染：not-measurable 消息 实际周期/频率 显式标 "N/A"、均匀性 "-"、符合性 "报文无时间戳，周期不可实测"。
- 表格下方加图例说明(为何 N/A + 手册 Trigger 机制)。

### 验证(重跑两套)
- bynav: #类/GGA/GST 显示真值；GPGSV/GLGSV/GAGSV/GQGSV/GBGSV/GPGSA 全标 N/A。
- huace: #类/GGA/GST 真值；6 种 GSV + GNGSA 标 N/A。
- **新发现(真实测量)**：huace SATVIS2A 实测 1.000s/1.00Hz vs 标称 10Hz → 🔴偏差-90%。数据实证：每历元约7条 SATVIS2A 同时发出(9772条0间隔)，历元间隔 1.0s。属真实设置差异，正是该告警的用途。

### 教训
- 周期统计只能基于报文自带时间戳；无时间戳的报文绝不能用其他报文时间轴"借"出周期——会得到看似完美实则虚假的 CV=0.00。
- 区分"标称周期"(配置/手册 Trigger)与"可实测"(报文带时间戳)。不可实测就诚实标 N/A。
